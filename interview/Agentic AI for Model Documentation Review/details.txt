## 3. Candidate Case Brief

这部分可以直接给候选人。

---

### Case Study: Design an AI Platform for Model Documentation Review

You are asked to design an internal **AI-assisted Model Documentation Review Platform** for a model validation team.

The platform is intended to support the review of model documentation submitted for validation, such as:

* model development documents
* methodology documents
* validation evidence packs
* testing summaries
* monitoring and change records
* implementation / architecture notes
* supporting annexes and templates

This is **not** a simple OCR tool, and **not** a standard chatbot or generic RAG assistant.

The target platform should support an end-to-end review workflow:

* ingest uploaded model documentation files
* extract and structure content from PDF, Word, PowerPoint, or templates
* review the submission against defined expectations, standards, and review rules
* identify gaps, inconsistencies, missing evidence, unclear claims, and areas requiring follow-up
* allow validators to inspect source evidence behind each finding
* allow human reviewer intervention, comment, and override
* support repeated review cycles after document updates
* maintain persistent records of review runs, findings, comments, and outcomes over time

Assume:

* some checks are deterministic and rules-based
* some checks require LLM-assisted semantic judgement
* some questions may require retrieval from policy / standards / review guidance
* outputs must be explainable, auditable, and evidence-linked
* the system should evolve from an MVP into a broader review platform

Please explain:

1. how you would define the product and key user journeys
2. what the MVP should include
3. how you would design the architecture and agent workflow
4. where rules, tools, retrieval, LLM reasoning, and human review fit together
5. how you would support persistence, review history, and repeated review cycles
6. what controls, risks, and evaluation approach you would use
7. how you would lead delivery of this workstream

---

## 4. Interviewer framing note

这份 case 的关键，是让候选人意识到：

* 它不是“问答”
* 它不是“帮我总结文档”

PDF 的课程版本里，系统被定义为对专业文档按规则自动检查并输出结构化问题列表；在合同场景下，重点是“保留坐标、可追溯、可定位、可修改”。这些思路迁移到 model documentation review 非常自然。

# 7. Core interview questions

---

## Q1. Product framing

**How would you define this product, and what problem is it solving for a model validation team?**

### 想听到的内容

* 是 model documentation review platform
* 不是 generic search assistant
* 核心是 review findings、evidence traceability、follow-up、repeat review
* 目标是提升 consistency、coverage、efficiency，而不是替代 validator judgement

### 为什么这题重要

PDF 里同样把系统定义成“按规则对专业文档进行内容和格式检查，并输出结构化问题列表”。

### Follow-up

* Why is this not just a RAG assistant?
* Why is this not just OCR plus summarisation?
* What makes model documentation review harder than normal enterprise document Q&A?

---

## Q2. User journeys

**What are the main user journeys in this platform?**

### 想听到的内容

* submission / upload
* parse and extract
* review run
* finding inspection
* evidence drill-down
* reviewer comment / override / assign follow-up
* resubmission / rerun
* compare versions
* close review / archive history

### Follow-up

* Who are the users: validators, SMEs, admins, model owners?
* What should a validator be able to do in the UI?
* What should a model owner see versus not see?

---

## Q3. End-to-end architecture

**How would you design the end-to-end architecture?**

### 想听到的内容

* document ingestion
* parsing / extraction
* content normalization
* chunking / section mapping
* review pack / rule engine
* retrieval of standards/guidance if needed
* semantic review with LLM
* findings store
* UI and API
* persistence / audit / rerun engine

### PDF reference inspiration

PDF 展示了“输入 PDF → 解析 → 审核 → 输出”的标准链路，并把系统分成文档解析模块、AI Agent 模块、规则系统模块。

### Follow-up

* Where would you separate parsing, review orchestration, and persistence?
* Would you use a state machine or graph workflow?
* What are the core data objects in the system?

---

## Q4. Rules vs LLM vs retrieval vs human review

**Where should deterministic rules, retrieval, LLM semantic reasoning, and human review each fit?**

### 想听到的内容

#### Rules

* required section checks
* metadata / template completeness
* required evidence presence
* field / date / identifier checks
* structural consistency checks

#### Retrieval

* policy / validation standard lookup
* review guidance lookup
* requirement mapping
* comparison against approved templates

#### LLM semantic reasoning

* assess whether methodology is clearly described
* detect vague claims
* assess whether evidence supports stated conclusions
* identify likely gaps or inconsistencies
* map narrative text to review expectations

#### Human review

* final materiality judgement
* disputed findings
* nuanced interpretation
* sign-off / challenge
* override decisions

### PDF reference inspiration

PDF 里把“规则系统模块”“AI Agent 模块”“外部知识检索”“规划/反思（Agentic模式）”分开描述，这一题正好对应。

### Follow-up

* What should never be left solely to the LLM?
* If the rules engine and the LLM disagree, what happens?
* Would you let the agent produce a final validation conclusion?

---

## Q5. Why agentic AI here?

**Why is this an agentic AI use case rather than a simple pipeline or one-shot prompt?**

### 想听到的内容

* multiple steps
* branching logic
* selective tool use
* requirement-based routing
* retrieval only when needed
* re-check after human input
* cross-document reasoning
* stateful rerun cycle

### PDF reference inspiration

PDF 明确说文档审核 Agent 的关键是“自主推理”和“工具调用”，并给出“先提取、再检索、再核对、再综合判断”的多步流程。

### Follow-up

* Where exactly would you use graph/state orchestration?
* Which steps are deterministic, and which are adaptive?
* What is the risk of over-engineering this with too much agent logic?

---

## Q6. Parsing, OCR, and evidence traceability

**How would you design parsing and evidence traceability for long model documents?**

### 想听到的内容

* OCR / parser selection by document type
* preserve layout and section hierarchy
* preserve page and bbox or source anchors
* handle tables, appendices, screenshots, diagrams
* normalize OCR issues
* section-aware chunking

### PDF reference inspiration

PDF 对长文档场景强调：

* OCR+RAG 更适合长文档
* 精确坐标定位与可追溯性非常关键
* 要按标题层级、段落语义切分
* 要保留 bbox_list 以便回到原 PDF 高亮问题。

### Follow-up

* When would you use OCR+text pipeline versus a VLM?
* How would you handle tables or annexes with important evidence?
* What should happen if extraction quality is poor?

---

## Q7. Chunking and review unit design

**How would you split documents into review units without losing validation context?**

### 想听到的内容

* section-aware chunking
* hierarchy-aware chunking
* keep evidence linkage
* retain section metadata
* avoid splitting across important logical units
* perhaps different review units for narrative sections vs evidence tables

### PDF reference inspiration

PDF 中的合同审核明确使用带坐标的 chunking，并且强调一个 chunk 会绑定多个 bbox，后续才能精确定位问题。

### Follow-up

* Would you chunk by heading, paragraph, token size, or document schema?
* How do you avoid missing cross-section inconsistencies?
* How would you debug poor chunking decisions?

---

## Q8. Review finding schema

**What should a structured review finding look like?**

### 想听到的内容

至少包括：

* finding_id
* case_id / run_id
* review_pack / rule_id
* category
* severity / priority
* finding type
* description
* source evidence
* page / location / anchor
* rationale
* suggested follow-up
* status
* reviewer override / comment
* created_at / updated_at

### PDF reference inspiration

PDF 的审核输出不是单段文字，而是 `issues`、`modifications`、`corrected_text`、`summary`、`overall_risk_level` 这类结构化对象；票据场景里也有字段、期望、实际、建议、总体状态。

### Follow-up

* Which fields should be deterministic?
* Which fields may be LLM-generated?
* How would you distinguish evidence-backed findings from inferred concerns?

---

## Q9. Repeat review cycles and persistence

**How would you support repeated review after the model owner updates documents?**

### 想听到的内容

* document versioning
* review run lineage
* delta comparison
* resolved / reopened / unchanged findings
* preserve reviewer comments
* allow partial rerun or full rerun
* persistent case history

### PDF reference inspiration

PDF 的产品雏形里已经出现“历史记录”，并且整个系统天然适合输出报告后整改再审。

### Follow-up

* What would be stored at case level vs run level?
* How would you stop overrides from being lost in reruns?
* Would you rerun all checks or only impacted checks?

---

## Q10. Controls and evaluation

**What are the main risks in this platform, and how would you evaluate quality?**

### 想听到的内容

#### Risks

* parser / OCR errors
* wrong rule logic
* hallucinated findings
* weak evidence linkage
* over-reliance by validators
* stale standards or review packs
* inconsistent output across reruns
* false sense of completeness
* poor access control

#### Evaluation

* benchmark document set
* expected finding set
* evidence correctness
* completeness recall
* precision of flagged issues
* reviewer acceptance / override rates
* rerun consistency
* section-level coverage

### PDF reference inspiration

PDF 里已体现出强结构化校验思路：多 Agent 结果、总体状态、详细问题、建议、导出 JSON 报告。

### Follow-up

* How would you evaluate semantic checks?
* What would a high override rate tell you?
* How would you prove the system is helping rather than creating noise?

---

## Q11. Delivery leadership

**If you were leading this workstream, what would you deliver in the first 8–12 weeks?**

### 想听到的内容

* one or two document types first
* one review pack first
* basic parsing + structured findings + evidence drill-down
* validator comment + override
* persistent review run history
* exportable report
* maybe no full automation of decisions in MVP

### Follow-up

* What would you deliberately leave out of MVP?
* What roles do you need: engineer, validator SME, product lead, platform support?
* What are the biggest delivery dependencies?
* How would you sequence pilot → controlled rollout → broader adoption?

# 8. High-value practical challenge questions

这些题最能识别候选人是否真的做过 agentic review system。

---

## Practical 1

**Suppose a required section appears to be missing based on template rules, but the LLM believes the content exists in a differently named section. What should the system do?**

### 强答案

* keep both signals separate
* classify as mapping ambiguity
* present evidence to reviewer
* do not silently let LLM override deterministic rule
* maybe improve section mapping logic later

这和 PDF 里“规则系统 + 语义理解”分层非常一致。

---

## Practical 2

**Suppose the parser extracts text from a scanned appendix badly, and an important validation evidence table is partially corrupted. How should the platform behave?**

### 强答案

* extraction quality flag
* dependent checks marked unreliable
* ask for manual review / alternative upload
* do not fabricate confident findings
* log parser failure clearly

PDF 里把文档解析质量视为落地关键，并展示了 OCR error cleaning、表格识别、阅读顺序修复等预处理思路。

---

## Practical 3

**How would you bind a finding back to the original document location?**

### 强答案

* preserve page + bbox / text anchor / chunk id
* match finding original text to bbox_list
* support front-end highlighting
* keep evidence references in finding schema

这几乎就是 PDF 合同审核方案的核心亮点。

---

## Practical 4

**If retrieval finds the relevant validation standard, but the final review comment is still weak or misleading, how would you debug it?**

### 强答案

* inspect retrieved sources
* inspect prompt assembly
* inspect chunk quality
* inspect whether the right requirement was mapped
* inspect evidence vs summary mismatch
* inspect output schema validation
* inspect traces by run id

---

## Practical 5

**Why would long model documentation often favor OCR/text+retrieval over end-to-end VLM review?**

### 强答案

* token cost
* long document handling
* structured chunking
* evidence traceability
* better section control
* better table handling in many workflows
* location grounding

PDF 对这点说得非常明确。

# 14. Why this pack is aligned with the PDF

这套 pack 与 PDF 的对应关系很清楚：

* **系统骨架**：PDF 用“输入→解析→审核→输出”的方式定义了文档审核系统。
* **Agentic 本质**：PDF 强调自主推理、工具调用、外部知识检索、多步规划。
* **模块拆分**：PDF 将方案拆成文档解析模块、AI Agent 模块、规则系统模块。
* **多 Agent 与编排**：PDF 的票据场景展示了完整性、格式、计算、业务规则四类 Agent，加上 Orchestrator 汇总状态和生成报告。

* **坐标追溯**：PDF 把 bbox_list、page、original text 映射作为核心逻辑，用于精确高亮问题位置。
* **结构化输出**：PDF 明确要求 issues、modifications、corrected_text、summary、overall_risk_level。
* **规则与优先级**：PDF 用 P0/P1/P2 和多种专业规则类型展示了如何做有层次的审核规则体系。
